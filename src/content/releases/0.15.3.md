### Fixed

- a library scan or a book's refresh read an unreachable library folder as the
  book's files having been deleted. It removed every tracked `File` row for
  that book and marked it `wanted` — which is what tells Audiobook Manager to
  go re-acquire it from indexers. A dropped network mount (NFS, SMB) presents
  on disk exactly like a folder someone emptied or deleted, and nothing
  distinguished the two, so an outage during a scan could wipe file records and
  queue an entire library for re-download.

  A book is now judged against the root folder it actually lives under rather
  than whichever root the scan happened to be walking, which is what made this
  worse the more root folders you had. A root that is missing is never trusted.
  A root that is merely empty only blocks the destructive path when that book
  already has tracked files — so a brand-new, empty root folder can still have
  its first folder created on it without being mistaken for an outage. A root
  that cannot be listed at all (a stale mount handle, an I/O error) is now
  treated as missing rather than healthy, which is the most common way a
  failing mount actually behaves.

  The same false reading reached three further places, all now fixed: applying
  fetched metadata set a book to `wanted` on an unreachable path before the
  scan's own check ever ran; refreshing a book reported "Refreshed book" on
  success when nothing had been touched; and a batch refresh counted every
  skipped book as a successful one.

- **a scan no longer creates a missing library root folder.** It used to create
  the folder and carry on, which is the same blind spot — an unmounted share is
  indistinguishable from a folder that was never made, and creating it destroys
  the evidence that anything was wrong. A missing root now stops the scan
  instead. If you relied on a scan to create your library folder, create it
  yourself first; adding a root folder already required the path to exist, so
  this only affects a scan against a root whose folder later went missing.

- the Health page reported root folders as accessible when a mount had dropped.
  It only checked whether the folder existed, so an empty mountpoint — the
  usual symptom — read as healthy. It now reports an empty root that still has
  books recorded under it as an error, while a new root folder with nothing in
  it yet stays healthy.

  A scan that skips books now says so on the Tasks page, rather than reporting
  no changes.

  Not covered: a mount that fails *below* a configured root folder — where the
  root itself is local and an inner folder is the mount point — still looks
  healthy from the root, and is handled as before.
